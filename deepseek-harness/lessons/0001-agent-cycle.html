今天只完成一件事

解释“请求模型 → 执行工具 → 带结果再请求模型”，并分清模型、循环、工具与会话记录的职责。

1. 模型提出调用，Harness 负责执行

假设用户说：“读取 notes.txt 并总结。”模型可以返回一个结构化的工具调用，例如 read_file({"path":"notes.txt"})。这表达它想做什么；Harness 的工具执行管线负责检查并调用对应实现，文件读取才真正发生。

工具返回“会议改为周五”后，这段文本进入会话记录。循环再发起模型请求，模型这次拿到包含工具结果的历史，才能给出“会议时间已改为周五”的答复。

① 模型提出工具调用② Harness执行获准的工具③ Session记录工具结果④ 模型根据结果继续回答

工具成功和这一轮完成，是两件事。工具完成一个具体动作；循环判断是否还需要模型请求或其他工作。

依据：Architecture · Turn flow；ReactLoopAgent.turn / step。本例的文件名、工具名与输出用于说明机制，不是一段已执行的真实会话。

2. 一轮 turn，可以有多个 step

Session 保存这段会话的事件记录；turn 是一轮工作的处理范围；step 围绕一次模型请求及其工具调用展开。在本例里，第 1 步要文件，第 2 步写总结，合起来是一轮 turn。

点“下一步”，观察右侧什么时候出现 tool/result，以及哪一步模型才拿到这份结果。

这张简图省略了什么？

真实流程先接纳输入和准备路由，再提交模型可见的输入；不是输入一到就直接追加 user/message。这里省略 system、request/header、request/context 等事件，以及实时流片段。

重试可能使同一个 step 发生多次请求尝试；输入被拒绝时，一个 turn 可以没有 step；取消、失败或工具的 concludesTurn 也可能提前结束。“有工具结果就再问一次模型”是本课正常路径，不是所有出口的规则。

核源：Turn flow；step 实现。

3. 你以后写的插件，会接到哪里？

在这个项目里，模型适配器、工具注册器、Session 和循环本身都由 Cordis 插件提供。插件是框架加载并管理生命周期的单元；工具是注册给模型调用的一项能力。一个插件可以注册工具，也可以只提供服务或监听事件。

部件本例中的职责服务入口
LLM生成文本或工具调用意图ctx.llm
Agent loop协调请求、工具执行与继续/结束ctx.agentLoop
Tools登记工具、检查并执行调用ctx.tools
Session记录事实，派生模型历史ctx.sessions

以后新增一个模型可调用的功能，先找 ctx.tools.register(...)；如果要观察耗时，就找相应事件。先学清扩展入口，再判断是否需要修改循环实现。

依据：Cordis 与扩展机制；官方首个工具示例。

4. 为什么这里还要专门学习 Session？

模型历史通过 session.deriveMessages() 从会话记录推导。设计要求是：影响模型请求的输入必须能从日志重建。但不是把全部日志直接发给模型；例如 turn 边界也会记录，却不是一条模型聊天消息。

因此，如果你的插件以后想给模型补充信息，只更新 UI 里的显示文本是不够的。你需要使用项目提供的上下文与日志机制；这会在会话一课里展开。

依据：Session log；Session.deriveMessages。日志提交和磁盘刷新也有区别，本课不把它们等同。

闭卷复述：本例有几个 turn、几个 step、几次工具执行？第二次模型请求比第一次多知道了什么？

1 个 turn、2 个 step、1 次工具执行。第二次请求的历史包含工具调用及其返回结果，模型获得了文件内容。关键是结果经记录进入新请求，而不是工具返回就自动等于模型已经回答。
