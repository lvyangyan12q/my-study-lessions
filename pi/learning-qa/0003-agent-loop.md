## 第一轮

### 问题 1：概念

用一句因果链说清：**「模型是无状态的」这个事实，对 agent 循环的结构提出了什么硬要求**？并指出：为什么「上下文压缩（compaction）」是这个事实的直接后果。

（要求写因果链：因为模型无状态 → 所以循环必须… → 于是数组只会… → 所以需要…）

#### 我的回答

因为模型无状态，所以每次调用大模型都是没有前文的信息的，所以agent调用大模型必须要把之前的对话信息整合到一起，一次性给模型。随着循环内容会越来越多，由于注意力机制和模型上下文窗口限制，所以需要上下文压缩

#### 批改

**通过。** 因果链完整：模型无状态 → 每轮必须把**整个 messages 数组一次性重发** → 数组只增不减 → 撑爆上下文窗口 → 需要压缩。这正是本课的「关键事实」。

- 一个该收窄的点：compaction 的**直接**依据是**上下文窗口有硬上限**（触发条件是 `contextTokens > contextWindow - reserveTokens`，见 `docs/compaction.md` / `learning-qa/compaction.md`）；「注意力机制」不在本课与文档给的依据里——结论虽不受影响，但**别把没核源的机制当理由**，这是本学科「不凭记忆下结论」的规矩。

### 问题 2：执行流程

场景：用户输入「统计 README.md 有多少行」。模型第一轮返回一条**带 toolCall 的 assistant 消息**。

(a) 按顺序写出 messages 数组内容的变化：从「只有 1 条」→「3 条」→ 到循环结束。每一步是**哪一行动作**让它变的。
(b) 「唯一的正常出口」落在 7 行的哪一行？判据是什么？
(c) 第 3 条消息（工具结果）为什么必须是**独立的一条消息**，而不是塞进那条 assistant 消息里？

（要求写出判断过程。）

#### 我的回答

a)「user:统计 README.md 有多少行」-》[user:统计 README.md 有多少行,assistant:toolcall读取readme]->[user:统计 README.md 有多少行,assistant:toolcall读取readme,tool:工具调用返回]-》[user:统计 README.md 有多少行,assistant:toolcall读取readme]->[user:统计 README.md 有多少行,assistant:toolcall读取readme,tool:工具调用返回,assistant:返回条数]

b)if (calls.length === 0) return.没有工具调用了，代表模型已经处理完了

c)因为这个是工具的调用信息，是需要告诉给模型工具执行的结果

#### 批改

**(a) 数组后半段对，中段错，且缺「哪一行动作」。**
- 正确骨架：1 条 →（模型返回带 toolCall 的 assistant）2 条 →（工具结果入栈）3 条 →（模型直接回答）4 条。
- **错在这里**：你中间插了一步把数组退回 `[user, assistant:toolcall]`（2 条）。**messages 数组只增不减**——7 行里没有任何一步会从数组里删消息。压缩也只是「不再发给模型」，原始条目仍留在会话里（阶段 7）。
- 还缺：每一步是**哪一行**造成的。对应关系：入栈 assistant = 第 3 行 `messages.push(msg)`；入栈工具结果 = 第 6 行 `for (const call of calls) messages.push(await runTool(call))`。

**(b) 通过。** 出口 = `if (calls.length === 0) return`（7 行的第 5 行）；判据 = 本轮模型没要求任何工具。补一句更准：这是**唯一正常**的出口，其余退出（`error` / `aborted` / `length`）都不算「任务完成」。

**(c) 没答到点上。** 「这是工具调用信息」不算理由。真正的理由两条：
1. **模型无状态、看不到副作用**——文件内容、命令输出对模型完全不可见，它只能读 messages，所以工具结果**必须**成为一条消息。
2. **角色必须分开**：那条 assistant 消息是**模型自己的输出**；工具结果是 **pi 产出**、role 为 `toolResult` 的独立消息。两套角色分开，模型才能区分「我说的」和「工具返回的」。塞进 assistant 消息就抹掉了这个区分。

### 问题 3：最小修改

给那个最小循环（7 行）加一个能力：**工具执行前先校验参数，参数不合法就当作一条错误结果回灌给模型，中途不要中断**。

(a) 这个校验落在 7 行里的**哪一步之前**？（写出那一步的名字）
(b) 最小改动是什么——在这 7 行里加在哪、加什么判断？
(c) 判断链：为什么它属于「循环体本身的必要动作」，而不是「堆在入口/出口的工程复杂度」？

#### 我的回答

runTool(call)在执行这一步前校验，校验不通过就把不通过的内容push到messages.因为调用报错需要告诉模型，让模型换调用方式参数，或者重新规划路径

#### 批改

**(a) 通过。** 落在**执行工具**这一步之前（7 行第 6 行，即 `runTool(call)` 之前）。

**(b) 基本对，漏了关键一点。** 校验不过就不执行工具、改为 push 一条结果消息——方向对。漏的是：这条消息必须是 **role 为 `toolResult`、带 `isError: true`** 的消息，不是普通消息；否则模型无法把它当作「这个工具出错了」来读。pi 里对应 `prepareToolCall()` 的 try 块 + `validateToolArguments()`，失败即走 `createErrorToolResult()`。

**(c) 未答。** 你答的是「为什么要回灌」（让模型换参数 / 重规划）——那是 (b) 的理由，不是 (c)。
(c) 问的是**分界**：7 行循环的四件必要动作里，「执行工具并把结果入栈」这一步本身就在**决定写回什么结果**——参数校验就是在决定「写回正常结果还是错误结果」，它**每一轮都发生在循环体内**，是那 4 件事的内在一部分。而「入口 / 出口的复杂度」（排队消息、中断、故障、压缩）管的是**循环何时进、何时出**，性质不同，校验不属于那一类。

## 强化练习

> 只练本轮薄弱点：①数组的单调性 + 工具结果的角色；②「循环体必要动作」与「入口/出口工程复杂度」的分界。共 2 题。

### 强化题 1：数组与角色

(a) 在一次会话的整个生命周期里，messages 数组会不会**变短**？举一个会被你误会成「数组变短」的场景（提示：压缩 / `/compact`），并说明真相。
(b) 工具执行完写回的那条消息，role 是什么？它和「模型自己说的那条 assistant 消息」在角色上**为什么必须分开**？

#### 我的回答

a)一般不会，一般只有压缩上下文会变短

b)toolresult.因为分开了模型才知道是工具调用的结果

#### 批改

**通过（(a) 有一处要修正）。**

- **(a) 方向对、结论要修。** 你点出了「压缩」正是那个会被误会成「数组变短」的场景，也说了「一般不会变短」——但要修正：**压缩也不会让 messages 数组变短**。压缩改的是「**下一次发给模型的上下文**」：从「全量历史」换成「摘要 + 保留段（从 `firstKeptEntryId` 起）」；而会话里的**原始条目一条不删**（压缩只是新增一条 `CompactionEntry` 记录）。准确说法是——「数组不缩，缩的是发给模型的请求」。这是阶段 7 的重点，先把这个区分记住。
- **(b) 通过。** role = `toolResult` ✅。补一句更本质的：**生成者不同**——assistant 是「模型说的」，toolResult 是「pi 产的」；分开模型才能区分「我说的」和「工具返回的」。

### 强化题 2：落层判断

下列三件事，各自属于「循环体内的**必要动作**（7 行）」还是「入口/出口的**工程复杂度**（为不信任环境而加）」？各用一句话说明理由。

(a) 工具执行前校验参数，失败就回灌一条 `isError` 结果。
(b) 循环本该结束了，但队列里又来了用户消息——决定要不要再转一圈。
(c) `stopReason === "length"` 时，把这条消息里的工具调用**整批判为失败**。

#### 我的回答

a)循环内做的

bc)入口/出口的**工程复杂度**（为不信任环境而加）

#### 批改

**三类全判对（(a) 的理由缺——只写了结论）。**

- **(a) 属循环体内的必要动作 ✅**。理由：它发生在「执行工具并写回结果」这一步内部、每轮都跑，是在决定「写回正常结果还是错误结果」——是 7 行四件事的内在一部分。
- **(b) 属入口/出口的工程复杂度 ✅**。理由：它管的是「循环何时结束 / 要不要再转一圈」，对应外层循环 + `pendingMessages`，是「不信任环境（用户随时可能打断）」换来的。
- **(c) 属入口/出口的工程复杂度 ✅**。理由：`stopReason === "length"` 说明「环境不可信」——输出可能被 token 上限截半、参数是残缺 JSON；这属于**故障保护**，不是四件必要动作。pi 里是 `failToolCallsFromTruncatedMessage()`。
