README：四种模式与定制阶梯

README 是 Pi 的官方地图。二次开发者要从里面带走两样东西：这个程序能以哪几种方式运行，以及一个需求应该落在定制阶梯的哪一层。

Pi 是什么

官方定位一句话：minimal terminal coding harness。默认只给模型四个工具：read、write、edit、bash。子代理、计划模式这类别家内建的功能，Pi 故意不做——原话是 adapt pi to your workflows, not the other way around：适配 Pi，而不是被 Pi 适配，且不必 fork 内核。这正是一切二次开发的前提。

四种运行模式

模式入口接口形态给谁用
interactivepi终端 TUI人在终端里对话
print / JSONpi -p、pi --mode json一次性文本 / JSON 事件流脚本调用
RPCpi --mode rpcstdin/stdout 上的 JSONL跨进程、非 Node 集成
SDKimport { createAgentSession }进程内 TypeScript API把 Pi 嵌进你自己的程序

你在 IDE 里打开过的 examples/sdk/01-minimal.ts 就是 SDK 模式的最小形态——十行代码建会话、订阅流、发一句话、清理。阶段 8 会正式回到它。

定制阶梯（从轻到重）

层是什么怎么触发放哪里
Prompt Template可复用的 Markdown 提示词/name 展开~/.pi/agent/prompts/、.pi/prompts/
Skill遵循 Agent Skills 标准的说明文档/skill:name 或模型按需自动加载~/.pi/agent/skills/、~/.agents/skills/、.pi/skills/、.agents/skills/
Theme颜色/样式 JSON（可热重载）设置选用~/.pi/agent/themes/、.pi/themes/
ExtensionTypeScript 模块：工具、命令、快捷键、事件、UI启动时自动加载~/.pi/agent/extensions/、.pi/extensions/
Pi Package把上面任意几样打包分发pi install npm:… / git:…npm 或 git 仓库
安全红线：Pi Package 以完整系统权限运行。扩展就是任意代码，Skill 可以指挥模型执行任何动作——装第三方包前必须读源码。

设计哲学 → 你的判断框架

核心刻意保持极小：没有内建 MCP，没有内建子代理和计划模式（README 明说这些用扩展实现）。接到一个二次开发需求时，按这个顺序问：

  1. 一段可复用提示词（Template）够吗？
  2. 一份操作说明（Skill）够吗？
  3. 需要跑代码、动工具/命令/UI（Extension）吗？
  4. 要分发给别人装（打成 Package）吗？
  5. 要在 Pi 之外调度 Pi（SDK / RPC）吗？
  6. 以上都不行，才考虑改内核源码。
这直接对应任务书的成功标准之一：能判断需求应由配置、Skill、Extension、SDK 还是内核修改完成。选层的默认原则：能用轻的不用重的，能装包不自写，能扩展不 fork。

动手

  1. 通读 README.md，重点四节：Quick Start、Customization、Programmatic Usage、Philosophy。
  2. 衔接第一课：用自己的话（不要翻批改）解释 README、docs/、examples/ 为什么出现在二进制发布包里。
  3. 自测一个场景：我想让每次会话结束自动 git commit——落在阶梯哪一层？为什么？
  4. 读完在对话里告诉我 完成：README.md，我出三个检索题。

完成标准

不看文件说出四种模式各自的入口和适用场景；面对一个新需求，30 秒内指出它属于阶梯的哪一层。
