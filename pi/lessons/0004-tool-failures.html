工具的四种失败

失败不是异常，是一条消息。

这节课结束时你能做到

说出工具失败的四种情形、它们的共同处置方式，并解释为什么"输出被截断"必须和另外三种分开处理。

前置（阶段 2 第 1 课）：循环里工具调用的结果必须写成一条 toolResult 消息回灌进 messages，因为模型只能读到这个数组。

一、一条原则

新手写 agent 最容易犯的错，是给工具执行套一个 try/catch，出错就 throw 出去。这样写出来的 agent 有致命缺陷：

反面对照

把错误抛到循环外面，外层的 catch 只能打印一行日志然后结束。结果是：模型永远不知道发生了什么。它看不到"工具失败了"这件事，因为你没把它写进 messages。用户拿到的是一个半成品答案，而模型还以为自己干完了。

正确的做法只有一句：把失败包装成一条消息，回灌给模型。

为什么？因为模型的全部输入就是 messages 数组。错误信息不在数组里，模型就看不见。把错误变成消息之后，模型下一轮有机会自己修正——换工具名、补参数、换个思路。

依据：packages/agent/src/agent-loop.ts 里的 createErrorToolResult() 与 createToolResultMessage()——错误结果和正常结果走的是同一个消息类型，只多一个 isError 标记。

二、四种失败

失败什么时候发生循环怎么处置
工具不存在 模型把工具名拼错，或者幻觉出一个没有的工具 返回 Tool X not found 错误结果
参数不合法 缺字段、类型不对、多传了东西 校验失败，返回校验器的报错文本
工具自己抛错 文件不存在、权限不足、命令返回非零 捕获异常，返回 error.message
参数被截断 模型输出撞上 token 上限（stopReason === "length"），工具参数可能只写了一半 整批不执行，全部返回错误，要求模型重新发起

前三种的处置完全一样：包成消息回灌。第四种不同，原因在下面的源码小节里。

三、逐帧看一次失败与自我修正

下面是工具层面的伪代码，以及它处理一次"工具名拼错"的全过程。注意 messages 数组：三次失败全部以消息形式留在里面，模型因此能一路修正。

四、源码里的四条分支

pi 把这些处置集中在两个函数里。第一段是工具查找与校验，第二段是执行，第三段是截断保护。

// prepareToolCall()：前三种失败
const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
if (!tool) {
  return { kind: "immediate",
           result: createErrorToolResult(`Tool ${toolCall.name} not found`),
           isError: true };
}
try {
  const validatedArgs = validateToolArguments(tool, preparedToolCall);
  ...
} catch (error) {
  return { kind: "immediate",
           result: createErrorToolResult(error instanceof Error ? error.message : String(error)),
           isError: true };
}

摘自 packages/agent/src/agent-loop.ts 的 prepareToolCall()。省略了 beforeToolCall 拦截与中断检查。

// executePreparedToolCall()：工具自己抛错
try {
  const result = await prepared.tool.execute(...);
  return { result, isError: false };
} catch (error) {
  return { result: createErrorToolResult(error.message), isError: true };
}
// runLoop()：截断保护，注意它不走 executeToolCalls
const executedToolBatch =
  message.stopReason === "length"
    ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
    : await executeToolCalls(currentContext, message, config, signal, emit);
为什么截断要单独处理

stopReason === "length" 表示模型的输出被 token 上限砍断了。工具调用是流式拼出来的，拼到一半停下时，参数的 JSON 可能刚好合法——能解析、能过校验，但内容残缺。比如要写 500 字只写进来 200 字。

前三种失败是"明显错了"，模型一看就知道；这种失败是静默错误，执行下去会产生看似正常实则错误的结果。所以 pi 一个都不执行，全部返回错误，逼模型重新发起。

pi 为此写的错误文案很直白：Tool call "X" was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.——把"为什么"和"怎么办"都告诉模型，它才能自我修正。

五、检验

先别看上面的表格和源码。

1. 说出四种工具失败，以及它们的共同处置方式。

工具不存在、参数不合法、工具自己抛错、参数被截断。

前三种的共同处置是：包成一条带 isError 标记的 toolResult 消息回灌给模型，绝不让异常冒泡出循环。第四种是整批不执行、全部返回错误，要求模型重新发起。

2. 为什么"工具失败"不该用 throw 让循环崩溃？

因为模型能看到的东西只有 messages 数组。异常抛到循环外面，错误信息就没进数组，模型下一轮完全不知道刚才失败了——它会以为任务已经完成，或者不停重复同一个坏调用。

把失败变成消息，等于给模型一次自我修正的机会。这是 agent 能自己修 bug 的唯一机制。

3. 工具执行时抛了异常，循环应该怎么做？

  • 中断循环
  • 回灌错误
  • 忽略错误
  • 重试一次

4. stopReason 是 length 时，为什么这批工具调用一个都不能执行？

  • 参数残缺
  • 工具缺失
  • 网络超时
  • 用户中断

任务

打开 pi/exercises/0002-tool-failures.mjs。这一课循环已经写好了，你只需要补 runToolCall()：把四种失败里的前三种（不存在、参数不合法、工具抛错）各自包成一条 isError 结果。

脚本自带判定：假模型会依次发起"拼错的名字""缺参数""会抛错的路径""正确调用"四次请求。做对了会打印每一步的 isError 序列（应当是真、真、真、假）并报通过；没有判定，就说明你漏了某条分支或把错误吞了。

主源推荐

packages/agent/src/agent-loop.ts 里的 prepareToolCall() 和 failToolCallsFromTruncatedMessage() 两个函数，一共不到 120 行，是"错误处理即数据"这个原则最干净的实现。

配套读 packages/agent/src/types.ts 里的 BeforeToolCallResult 与 AfterToolCallResult——它们回答了"如果想在工具前后插手，官方给了哪两个口子"。

有不清楚的地方直接问我。这一课最容易含糊的一点是：错误消息的文案到底写给谁看。答案是写给模型看，所以它必须包含"为什么失败"和"应该怎么重试"——这是提示工程的一部分，不是日志。下一课讲流式输出与事件流。
