Providers：认证与凭据解析

这篇讲「Pi 怎么拿到访问模型的凭据」。它本身是清单，但有一个核心判断：当好几处都配了凭据时，Pi 按固定顺序挑——先命中的胜出。搞清这个顺序，后面接自定义 provider、排查「为什么它不用我的 Key」都靠它。

这一课带走什么

能说出四种认证来源、凭据存在哪；能背出凭据解析的四级优先级；知道 /logout 到底删了什么、没删什么。

核心：凭据解析顺序（高一低，第一个命中即胜出）

一个补充优先级：存下的 API-key 凭据里可以带一个 env 对象，它的值优先于进程环境（同一 provider）。例：把 CLOUDFLARE_ACCOUNT_ID 放进凭据的 env，就盖过 shell 里的同名环境变量。

认证方式

方式说明
OAuth 登录浏览器或设备授权流；/login 引导并保存结果
API key直接在 /login 里存入，或用环境变量提供
云端 ambient 凭据Amazon Bedrock、Google Vertex AI 可用平台自带凭据

用 /login [provider] 查看某个 provider 支持哪些方式。

凭据存在哪：auth.json

  • /login 走完 OAuth 或 API-key 流程后，凭据存进 auth.json（agent 目录下）。
  • 远端 / 无头机器上 OAuth 回调可能回不到本进程：按提示把**最终重定向 URL 或授权码**粘回 Pi。
  • /logout 只移除存下的凭据——它不会取消环境变量、不会删 models.json 里的认证、也不会在 provider 那边吊销该凭据。
  • auth.json 里可能有 API key 和 OAuth token：保密、别提交。

不落盘的两条路

用环境变量（CI 首选）

export ANTHROPIC_API_KEY=sk-ant-...
pi

单主变量示例：Anthropic→ANTHROPIC_API_KEY、OpenAI→OPENAI_API_KEY、Gemini→GEMINI_API_KEY、DeepSeek→DEEPSEEK_API_KEY（完整表见原文）。Anthropic 还认 ANTHROPIC_OAUTH_TOKEN（API 凭据）与 ANTHROPIC_AUTH_TOKEN（bearer）。

用命令取 key（不写进磁盘）

{
  "anthropic": {
    "type": "api_key",
    "key": "!security find-generic-password -ws 'anthropic'"
  }
}

key 以 ! 开头时，Pi 在**首次需要该 key 时**执行命令、并缓存它的标准输出到进程结束。空输出、超时或非零退出 → key 保持未解析，直到重启。
