packages/agent：Message Flow 与 Event Flow

第 3、4 课看的是循环的内部结构；这一篇看它的两条边界——喂进去的消息怎么变成 LLM 认得的样子（Message Flow），跑起来时又吐出哪些事件给 UI（Event Flow）。这两条边界，就是以后写 Extension / SDK 时要对接的口子。

这一课带走什么

画出消息流的两步转换；说出一次 prompt() 的事件顺序；知道 AgentMessage 与 LLM Message 为什么是两套。

核心一：Message Flow（进边界）

  • transformContext：修剪旧消息、注入外部上下文（**可选**）。
  • convertToLlm：过滤掉 UI 专用消息、把自定义类型转成 LLM 格式（**必需**）。
为什么要两套类型？AgentMessage 更宽，能塞应用自己的消息（靠声明合并扩展）；LLM 只懂 user / assistant / toolResult。convertToLlm 就是这两者之间唯一的桥——**只在每次 LLM 调用边界发生一次**。

核心二：Event Flow（出边界）

调用 prompt("Hello") 时，事件按下面的顺序发出（无工具）：

事件类型表

事件含义
agent_start / agent_end整轮运行的开始 / 结束（agent_end 是最后一个事件）
turn_start / turn_end一轮 = 一次 LLM 调用 + 它的工具执行
message_start / message_end任意消息（user / assistant / toolResult）开始与结束
message_update仅 assistant：带 assistantMessageEvent 增量（流式）
tool_execution_start / _update / _end工具开始 / 流式进度 / 结束

agent.subscribe() 的回调**按注册顺序被 await**；agent_end 之后不再有循环事件，但 waitForIdle() / prompt() 要等所有 agent_end 订阅者结束才 settle。

顺带记两条（后面会用到）

  • 工具执行模式：默认 parallel（并行）；只要批里有一个工具声明 executionMode: "sequential"，整批顺序执行。并行时**完成事件按完成顺序**，但持久化的 toolResult 消息仍按 assistant 源码顺序。
  • 四个钩子：beforeToolCall（校验参数后、执行前，可 block）、afterToolCall（执行后、发最终事件前，可改写）、prepareRequest（每次请求前重建上下文）、finishTurn（turn 结束前决定 continue / end）。扩展的权限门禁、审计都挂这里。
