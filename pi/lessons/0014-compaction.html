Compaction：上下文满了怎么办

模型没有记忆，每轮都要把整段历史重发。历史越长越贵、最终撑爆窗口——于是 Pi 把旧消息**摘要**掉。这一课的重点是：**切点在哪、为什么不能切在工具结果上**。

这一课带走什么

画出压缩前后的条目序列；说出切点规则与 firstKeptEntryId 的作用；分清 compaction 与 branch summarization。

核心：切点与 firstKeptEntryId

切点规则（最该记）

绝不在 tool 结果处切——工具结果必须和它的工具调用待在一起。可以在 user / assistant / BashExecution / 自定义消息处切。

五步：① 从后往前累计 token 找切点（到 keepRecentTokens，默认 20000）→ ② 取要摘要的消息 → ③ 调 LLM 生成摘要 → ④ 追加 CompactionEntry（含 summary 与 firstKeptEntryId）→ ⑤ 重建上下文。重复压缩从上一次的 firstKeptEntryId 起。

两种摘要

机制触发目的
Compaction上下文超阈值，或 /compact摘要旧消息，腾上下文
Branch summarization/tree 导航换分支时保留离开分支的上下文

扩展钩子：session_before_compact、session_compact_failed、session_before_tree。

检索练习（合上再答）

压缩的切点能不能落在工具结果上？为什么？

不能。工具结果必须和它的工具调用待在一起；切在中间会让模型拿到「没有对应请求的结果」。

下面哪种位置不能作为切点？

  • 工具结果
  • 用户消息
  • 助手消息
  • 系统消息

为什么会有 compaction？

  • 上下文满
  • 磁盘太小
  • 网络延迟
  • 模型选择
